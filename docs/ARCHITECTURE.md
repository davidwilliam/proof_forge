# Architecture

This describes the system as built. Each section names the code that implements it.

## Components

| Component | Code | Role |
|---|---|---|
| Task | `formal/`, `tasks/<id>/`, `harness/task.py`, `harness/lock.py` | one locked Lean project: protected spec, challenge, executable wrapper, oracle |
| Judge | `harness/judge.py` | decides proof acceptance from exit codes only |
| Library | `lib/`, `harness/fin_lib.py`, `harness/FinIndex.lean` | ProofForgeFin: vendored into judged projects, bound into Passports, indexed for the repair agent |
| Proof harvesting | `harness/harvest.py` | helper lemmas of verified candidates into `ProofForgeFin.Harvested`, with provenance; `docs/HARVEST.md` |
| Binary check | `harness/binary_check.py` | rebuilds the executable and runs requirement-derived property tests |
| Counterexample stage | `harness/counterexample.py`, `counterexamples/` | turns a refuted requirement's witness into a refutation checked by the kernel |
| Passport | `harness/passport.py`, `bin/proofforge` | assembles statuses, hashes and provenance; reproduces a Passport |
| Repair agents | `agents/repair.py`, `agents/baseline.py`, `agents/meta_client.py`, `agents/budget.py`, `agents/portfolio.py`, `agents/ledger.py`, `agents/leanserver.py`, `agents/refute.py`, `agents/variants.py` | Meta models fix the code and write the proofs; a tactic portfolio before model turns; attempt ledgers and resumption; a persistent Lean session for proof states; refutation of new helpers on concrete values; parallel short variants |
| Evaluation | `eval/e1.py`, `eval/e2.py`, `eval/freeze.py`, `harness/ordinary.py` | completion under equal budgets (E1); integrity of checking (E2) |
| PR gate | `.github/workflows/proofforge.yml` | judges a pull request's candidate from a trusted checkout |
| API and web | `server/app.py`, `server/controls.py`, `web/` | jobs, replays, checks, Passports, the payout and swap sidecars, the hidden challenge |
| Images and hosting | `infra/docker/`, `infra/fly/`, `infra/vercel/` | pinned Lean image; Fly.io Machine for the API and judge; Vercel for the web |

## Task

A task is a self-contained Lake project (format in `docs/TASKS.md`). `spec/<Lib>/Spec.lean` defines the requirement predicates over the implementation; `spec/<Lib>/Challenge.lean` states the definition holes and the required theorems with `sorry`; `spec/comparator.json` names the challenge and solution modules, the theorems, the definitions under repair and the permitted axioms (`propext`, `Quot.sound`, `Classical.choice`). `harness/lock.py` writes `spec/locked.json`: the SHA-256 of every protected file and a manifest hash over them. `oracle.py` is an independent Python model of the component used only by the binary check. The candidate is `candidate/Solution.lean` (and optionally `candidate/Lib/**`); it is the only input taken from an agent or a pull request.

## Judge

`judge.judge(candidate, task)` runs, in order:

1. Tree check. Every protected file present in the submitted workspace must be byte-identical to `spec/locked.json`; the lock must be internally consistent, cover exactly the protected files, and match the repository's copies.
2. Implementation scan. After stripping comments, the candidate must not contain `implemented_by`, `extern`, `unsafe`, `@[export]`, `macro`, `elab`, `syntax`, `initialize`, `#eval`, `run_cmd`, `run_elab`, `run_meta`, `native_decide`, `set_option`, `opaque`, `axiom` or `@[csimp]`, nor any other way to define or run elaboration-time code: `elab_rules`, `macro_rules`, `run_tac`, `by_elab`, simprocs, `register_*`, `declare_*` and `builtin_*` commands, module-system `meta` declarations, and attributes that register code (`@[tactic]`, `@[term_elab]`, `@[command_elab]`, `@[macro]`, `@[delab]`, `@[init]` and the like). It may import only the task's `Spec` and `Lemmas`, `Init.*`, `Std.*` and `ProofForgeFin.*` (the library below; `ProofForgeFinDemo` and `Lean` are refused). Importing `ProofForgeFin` brings `Lean` into scope, because the library's tactics are metaprograms; the metaprogram rules above are what keep candidate code from defining its own. This is defense in depth against code overrides and elaboration-time code; Comparator is the authority on statements.
3. Fresh project. A new temporary directory receives the locked project files from the repository (`lean-toolchain`, `lakefile.toml`, `lake-manifest.json`, `spec/`, `app/`) and the candidate files, nothing else. It has never been built. When a candidate file imports a `ProofForgeFin` module, the library is vendored into it (next section); otherwise the directory is exactly the locked files and the candidate.
4. Comparator: `lake comparator --paranoid --config spec/comparator.json`. Comparator builds the solution in its bubblewrap sandbox, checks that every required theorem has exactly the challenge's statement, with the definitions under repair supplied by the solution, checks that only the permitted axioms are used, and checks the declarations with six kernels: Lean's default and paranoid modes, lean4lean, nanoda, con-leche and con-ron. Any failure rejects the candidate.
5. leanchecker: `lake build Solution && lake env leanchecker Solution`, a kernel replay of the solution module's declarations. It runs without `--fresh`, so imported modules (the locked spec and Lean's core library) are loaded from their build outputs rather than replayed; Comparator's kernels above check the solution's declarations independently.
6. Axiom audit: `#print axioms` for every required theorem. The result is recorded per theorem in the Passport; enforcement of permitted axioms is Comparator's.

The candidate is accepted only if steps 1, 2 (including the library scan below), 4 and 5 succeed. Lean runs in the pinned image `proofforge-lean:4.35.0` (`infra/docker/Dockerfile.lean`: the Ubuntu 24.04 base pinned by digest, elan 4.2.4 and Lean v4.35.0 from their GitHub releases, each checked against its published SHA-256; the apt packages, among them bubblewrap, come from the Ubuntu archive at build time, so a rebuild can produce a different image digest, and every Passport records the digest it ran under). Locally each run is a `docker run --network none --memory 4g --pids-limit 512` container with the namespaces bubblewrap needs; inside the image (the Fly host, `PF_IN_IMAGE=1`) commands run directly and Comparator's sandbox applies the same way. Concurrent Lean runs per host are bounded by file locks (`PF_CONTAINER_SLOTS`, default 2). Every run has a timeout; callers can impose a request-wide deadline (`judge.time_limit`), and a run stopped by it is marked as a timeout, never as a failure of the candidate.

## ProofForgeFin in judged projects

`harness/fin_lib.py` makes the library in `lib/` (Lake package `proofforge-fin`, library `ProofForgeFin`; contents in `lib/README.md`) available to candidates.

- Version. `source_tree_sha256` is a SHA-256 over the relative path and SHA-256 of every file the package is built from: `lakefile.toml`, `lake-manifest.json`, `lean-toolchain`, `ProofForgeFin.lean` and `ProofForgeFin/**/*.lean`. `ProofForgeFinDemo`, `Audit.lean` and the docs are not part of the package, so no candidate can import the demonstrations.
- Build. Each version is built once per host, in the pinned image with no network, from those sources: `lake build ProofForgeFin ProofForgeFin:static` (the `.olean` files and the native objects an executable that imports the library links), in a cache directory keyed by the version (`PF_FIN_CACHE`, default `<tmp>/proofforge-fin`; the API image builds it at image build time). The same run writes the declaration index (`harness/FinIndex.lean`). Lake's build traces are content hashes, so a copy of the built package is up to date in any directory; a cached package whose sources do not hash to the expected version is refused.
- Vendoring. When a candidate file imports a `ProofForgeFin` module, the fresh project of the judge, of the binary check and of the counterexample stage gets the built package at `.lake/packages/proofforge-fin` (inside `.lake`, the only directory Comparator's sandbox lets a build write), a `[[require]]` with that path appended to its `lakefile.toml` and the matching path entry in `lake-manifest.json`. Comparator resolves the dependency inside its sandbox from the manifest; nothing is fetched. A candidate that imports no library module gets the same fresh project as before the integration.
- Library scan. The library modules the candidate imports, transitively, are scanned with a library policy: no `implemented_by`, `extern`, `unsafe`, `@[export]`, `@[csimp]`, `initialize`, `#eval`, `run_cmd`, `run_elab`, `run_meta`, `native_decide`, `bv_decide`, `set_option`, `opaque`, `axiom`, `sorry` or `partial`, and imports only from `ProofForgeFin`, `Init`, `Std` and `Lean`. Tactic and syntax definitions (`syntax`, `macro`, `elab_rules`, simprocs, `register_simp_attr`) are allowed in library code, not in candidate code: they change how a proof is found, not what the kernels check. The library sources are part of the trusted checkout and bound by hash in the Passport.
- Checking. The export Comparator checks contains every constant the required theorems depend on, library declarations included (1,872 declarations for `req_no_backdated` of `rw-compound-comp` with the library), so all six kernels check the library declarations a solution uses; the axiom audit covers them through `#print axioms`. `leanchecker` replays the solution module and loads the library from its build outputs, as it does for the locked spec.
- Kernel check of the library. `harness/fin_kernels.py` (test `tests/test_fin_kernels.py`) holds every library and demonstration declaration to the same kernels, so no candidate is rejected for a library declaration a kernel does not accept. It builds `lib/` in the pinned image, lists every constant its modules declare (`harness/FinDecls.lean`), exports them with the toolchain's `leanexport` plus Comparator's own export targets, and runs `lake comparator --paranoid --challenge-from-export E --solution-from-export E` with every theorem named and the judge's permitted axioms: Comparator's statement comparison, axiom check and six kernels, with its command lines and sandbox, on that export. A kernel stops at its first rejection; the checker names the declaration (con-leche and con-ron are re-run with one worker to print it), removes it and its dependents, and runs Comparator again until every kernel accepts, then checks each rejected declaration alone. The `_unsafe_rec` constants Lean compiles recursive definitions to are checked separately with `lake check --paranoid --from-export`: nanoda, con-leche and con-ron decline `unsafe` definitions by design and no proof term mentions one. `leanchecker` replays every module. A candidate's export holds the same library constants from the same build, and each kernel checks a declaration against the declarations it depends on, so the verdict per declaration carries over.

Choice. The library is vendored from the committed sources rather than baked into a new judge image. The judge image stays `proofforge-lean:4.35.0` at the digest every committed Passport records, so those Passports reproduce unchanged; a library change needs no image rebuild, only a new build of the library, keyed by the new source tree hash; the library version is visible in the repository and in the Passport rather than inside an image layer; and the build uses the same pinned toolchain and the same offline container as the judge. The cost is one library build per version per host (about 35 s for 56 modules on the development machine), and a candidate that imports the library adds the time to copy the built package (56 MB) to each fresh project.

Experiment: `tests/fixtures/library/compound_lib.lean` is a candidate for `rw-compound-comp` that imports `ProofForgeFin.DeFi`; its implementation and per-call proofs are the reference solution's, and its three sequence bounds are the library argument of `lib/ProofForgeFinDemo/DeFi/Compound.lean`. It is VERIFIED with all eight requirements, six kernels, `leanchecker` and the axioms `propext`, `Classical.choice` and `Quot.sound`, on the host and inside the image (`PF_IN_IMAGE=1`). As first written in the demonstration, four steps were accepted by Lean's kernels, lean4lean and nanoda but not by con-leche and con-ron ("fuel exhausted: whnfCore"): those two kernels unfold `doubleScale = 10 ^ 36` in equations such as `A * doubleScale + 0 = A * doubleScale`. The fixture and now the demonstration prove that arithmetic over an abstract scale and instantiate it, the agent prompt with the library says so, and `harness/fin_kernels.py` checks every library declaration against all six kernels.

## Binary check

`binary_check.check_binary` builds the task's executable (`lake build <exe>`) in another fresh project from the same locked files and candidate, records its SHA-256, and runs JSON-lines cases through it. Round 1 is the oracle's flagship case plus N generated cases (2,000 for Passports, seed 0; the E1 evaluator uses seed 1). Round 2 runs follow-up cases the oracle derives from round-1 outputs, such as resubmitting an applied transaction. `oracle.check` maps each output to requirement IDs it violates; the first six witnesses (input, output, message) are kept, plus the first witness of every further requirement, so each refuted requirement has one. A witness found on a follow-up case also records the round-1 case and output it came from (`origin`). Status is `PASS`, `REFUTED`, `BUILD_FAILED` or `TIMEOUT`.

The executable wrapper `app/Main.lean` (JSON parsing and printing) is locked but not proved; the Passport labels it tested only.

## Counterexample stage

`counterexample.run` (called by `passport.run(..., counterexample=True)` and by `bin/proofforge check` for a REFUTED candidate) takes the witness of each refuted requirement and writes a Lean theorem `<ns>.cex_<req_theorem> : ¬ (<locked statement>)`. The statement is the locked challenge's, negated; an optional per-task adapter (`counterexamples/<task or base id>.py`, or `<task>/counterexample.py`) supplies the Lean terms of the instance, and the default proof instantiates the requirement and decides the rest by kernel evaluation. In a fresh project with the locked files and the candidate, the refutation is built, then checked with `lake comparator --paranoid` against a challenge that is the locked `Challenge.lean` with the negated theorem appended, then with `leanchecker` and `#print axioms`. Details and the trust argument are in `docs/COUNTEREXAMPLES.md`.

## Passport

`passport.build` combines one judge record and one binary record:

| Requirement status | Condition |
|---|---|
| VERIFIED | the judge accepted and the binary passed every case |
| REFUTED | the binary violated this requirement on a concrete input (witness recorded) |
| UNRESOLVED | anything else, including a rejected proof without a witness and a check stopped by a time limit |

The component is VERIFIED only if every requirement is, REFUTED if any requirement is, and UNRESOLVED otherwise. The Passport records the task and manifest hashes, the statement of each requirement, the candidate and solution-tree hashes, the executable hash and the platform it was built for (for example `linux/amd64`), the Lean toolchain and judge image digest, the library record (`library`: the ProofForgeFin source tree hash available to the judge, whether it was vendored, and for a candidate that imports it the modules imported, the number of modules in their closure, the library scan, the commit whose library sources are the vendored ones, and the image and toolchain the vendored build was made with), per-check exit codes and timings, the six kernel names, the axioms per theorem, the trust assumptions, model and budget provenance when an agent produced the candidate, and a reproduce command. A REFUTED Passport issued with the counterexample stage also carries `counterexamples`: per refuted requirement, the negated statement, the witness, the Lean source of the refutation and its hash, the kernels that accepted it and its axioms, or the reason it was not checked; the requirement statuses are unchanged. `passport_sha256` is a hash of the canonical JSON without that field. `bin/proofforge verify passport.json --candidate PATH` re-runs the pipeline and compares every recorded hash and status; for a Passport with `counterexamples` it also re-checks each recorded refutation in a fresh container against a challenge regenerated from the locked files. An executable built for another CPU architecture has a different hash, so the executable hash is compared only when the machine builds for the Passport's platform; the rebuilt executable's test result is compared in every case, and the output says when the hash was not compared. Verify also compares the Lean toolchain and the library record: whether the library was vendored and, if so, its source tree hash, the modules imported and the library scan. A Passport issued before the integration has no library record, and its candidate must not import the library. A Passport whose library version is not the checkout's is reproduced with the library sources of the commit it records, extracted from git into the cache; without that commit the source tree hash is reported as different. The judge image digest is reported and counted as a difference only with `--strict-image`, because a rebuilt image can have another digest.

## Repair agents

All agents call the Meta Model API through `agents/meta_client.py` (chat completions with tool calls; transient network errors are retried within the run's deadline).

- A0, compile-and-retry (`agents/baseline.py`): Muse Spark 1.3 receives the brief, the spec and the buggy file and returns a complete `Solution.lean`; the harness replies with Lean errors, or with the axiom audit and scan violations once it compiles. No tests, snippets or planner.
- A1, harness (`agents/repair.py --planner none`): Muse Spark 1.3 works through tools in a private copy of the task without reference solutions: `read_file`, `write_solution`, `replace_declaration`, `try_snippet` (compiles a snippet after the current file and banks its proved declarations), `check` (per-theorem PROVED, SORRY or ERROR with goal states) and `run_tests` (the binary check). Phase 0 fixes behavior until the tests pass; phase 1 runs one dialog per obligation; phase 2 retries what is left; phase 3 spends any remaining budget on whole-file repair. Banking a proved snippet is transactional, and the run's result is its last compiling version.
- A2, harness with planner (`--planner muse-wonder-1.0`): in phase 2 Muse Wonder proposes helper lemma statements for an obligation that resisted direct proof; they are installed as `sorry` targets and proved by Spark, recursively to depth 2. Helpers left unproved and unused are pruned.
- Library (`agents/repair.py --library on|off`, default on; A1 and A2 only): with the library on, the session workspace has ProofForgeFin vendored, the system prompt gains a section generated from the library's declaration index (the rule that the candidate may import ProofForgeFin modules, every module with the opening of its doc, every tactic with one line on when to use it, the simp sets), the tools gain `search_library` (BM25 over each declaration's name, signature, doc string and module in the index `harness/FinIndex.lean` generates from the built library) and `add_import` (transactional), and each obligation's prompt lists the eight declarations the index ranks highest for the obligation's statement and the doc strings of the specification definitions it names. Phase 3 gets the library section without the tools. `summary.json` records `library` (enabled, source tree hash, index hash, number of entries), and `eval/e1.py --library on|off` passes the flag to A1 and A2 and records it in `config.json`. A0 is unchanged: its prompt, tools and workspace have no library. The E1 results in `results/e1-dev-2` and `results/e1-test-1` were produced before the library existed.

`agents/budget.py` enforces a dollar cap and a wall-clock cap per run. Dollars are counted at standard-tier list prices for every model, including calls served by the Contributor tier, so arms compare on one scale; the amount actually charged is tracked separately. Each call is charged its worst case before it is sent and settled from reported usage. The agent never decides acceptance; its last compiling version is judged by the shared evaluator.

### Top-down loop (`--loop topdown`)

`agents/repair.py --loop topdown` keeps phase 0 (behavior first) and phase 3 (whole-file repair) of the orchestrated loop and replaces phases 1 and 2, which work obligation by obligation in the task's listed order, with two phases. The orchestrated loop stays the default.

- Structure phase. The planner (A2) writes a proof skeleton from the spec, the candidate, the unproved required theorems and, with the library, the declarations the index ranks highest for them and for reduction theorems (hypotheses about one step, conclusion about every sequence). The skeleton gives each required theorem a proof from named helper theorems whose proofs may be `sorry`, plus any definitions they need with complete bodies. It is installed and kept only if the file compiles and a Lean probe of the compiled candidate (`DEPS_PROBE`: for every declaration of the `Solution` module, whether its own type or value mentions `sorryAx` and which candidate declarations it uses, with compiler-generated auxiliaries merged into their owner) shows that no required theorem mentions `sorry` in its own proof, that no definition is left open, that no refuted helper is used and that every helper left open is used by some required theorem (a helper that no proof uses would be deleted as unused, losing the step the architect meant it for; the architect is asked to write the proof that uses it, for example the induction from a one-step helper to a statement over every sequence, or to leave it out). Rejections go back with the reason; the planner gets `--skeleton-tries` replies (default 3). In A1, or if the planner fails, Spark writes the skeleton in a tool dialog (`submit_skeleton`, `read_file`, `try_snippet`, `search_library`, `add_import`; `--skeleton-turns`, default 12). A skeleton may not use `namespace`, `section` or `variable`; `import ProofForgeFin...` and `open` lines are handled as in `try_snippet`. If no skeleton is accepted the run continues with phases 1 and 2 of the orchestrated loop.
- Fill phase. The open obligations are the helper declarations that mention `sorry` and that some required theorem depends on, read from the same Lean probe after every round. They are dispatched through the orchestrated loop's `resolve` (a focused dialog with snippets and library hints, then a planner decomposition in A2), helpers used by more required theorems first, then those the library index matches best (BM25 score of the top hit), then file order. Obligation dialogs also get `refute_helper`: a proof of `¬ (type_of% @helper)` that Lean accepts with no sorry marks the helper false. When a helper is refuted, or every open helper has had `--helper-attempts` resolutions (default 2), a revised skeleton is requested with the refutations, the end of the failed attempts and the helpers already proved (`--restructures`, default 2). A round repeats while helpers stay open, up to `--fill-rounds` (default 6). When nothing is open the required theorems are proved and the official judge is run in the session.
- Prompt size. In the top-down loop the candidate is shown to the dialogs and the planner with the proofs of proved theorems of four lines or more elided (`compact_view`; the file is unchanged), `read_file` returns that view for candidate/Solution.lean and one declaration in full when given `name`, and `search_library` returns at most 10 hits. Replayed on the messages of a recorded A2 top-down run on rw-compound-comp, this removes about 1.9M of the prover's 11.5M prompt tokens. The other loops are unchanged.

Budget accounting and stop rules are those of the other loops: every model call goes through `Session.call` and `agents/budget.py`, and every Lean run stops at the deadline. New event kinds in `events.jsonl`: `skeleton` (round, source planner or prover, attempt, accepted, the problems of a rejection, or for an accepted skeleton the derived required theorems, the open helpers with the required theorems that use each, and hoisted imports), `deps` (per fill round: required theorems proved, those with a direct `sorry`, open helpers and their users), `fill_order` (the helpers of a round in dispatch order with users, library score and attempts), `helper` (one resolution: name, users, ok, attempt, refuted), `refute` (a `refute_helper` call and whether Lean accepted it), `fill_end` (done, restructure or stalled), `restructure` (refuted and stuck helpers), and `phase` with the values `structure`, `fill` and `obligations`. The skeleton code of each accepted round is saved as `skeleton_<round>.lean` and the planner's replies as `skeleton_<round>.md`.

Snippets in every loop: `import` lines in a `try_snippet` snippet are moved to the scratch file's header when they name a ProofForgeFin module (and added to the candidate with `add_import` when the snippet compiles); any other import is refused without compiling, with the reason. Top-level `open` lines in a snippet apply to its later declarations, which are compiled and banked as `open ... in <declaration>`. A clean snippet with several new declarations is banked with one compile (one at a time, as before, if that compile fails). A proved version of an open helper stays in place when it uses nothing declared after it, so declarations that already use the helper keep compiling, and otherwise moves to the end; the other placement is tried if the first does not compile. Pruning unused open helpers skips dotted names (dot notation uses them without naming them) and is reverted if the file no longer compiles. The library section of the prompt describes reduction theorems as a general pattern.

### Tactic portfolio (`--portfolio on|off`, default on)

`agents/portfolio.py`. Before the model spends a turn on an open goal (a required theorem still proved by `sorry`, a skeleton helper, a planner lemma, a goal a resumed attempt left open), the harness tries a fixed list of Lean tactics on it: `grind`, `omega`, `simp_all`, `decide`, `simp_all <;> omega`, the library's `generalize_divs <;> omega` and `machine_norm <;> grind` when a module the candidate imports defines them, `unfold D at *; intros; grind` and `intros; grind [D]` where `D` are the definitions the goal's own statement names (found in the locked spec files and the candidate, never chosen per task), `exact?` and `try?`. Nothing is task-specific.

- One compile per batch. The batch file is the current candidate with the goals removed (no tactic can use a goal to prove itself), then a renamed copy of each goal per tactic under `set_option maxHeartbeats N in` (the per-tactic limit, `--portfolio-heartbeats`, default 50000 against Lean's 200000), with the searching tactics first so that no copy they could find exists yet, then `#print axioms` of every copy. It is compiled with `lake env lean --json`, so every message carries its position; the profiler's trace gives each attempt's time. A copy closes its goal when Lean reports no error for it and its axioms do not include `sorryAx` (so it uses no open declaration either). The batch is stopped after 60 s plus `--portfolio-seconds` (default 5) per attempt. `exact?` and `try?` are not bounded by the heartbeat limit (in the replay one ran 516 s), so a stopped batch is compiled once more without them.
- Banking. The first closing entry in list order is banked with `Session.bank`, the banking path of `try_snippet`: the goal's own statement with the tactic as proof, kept only if the whole candidate compiles. `exact?` and `try?` are banked as the proof they report (their `Try this` suggestion), never as the search; a suggestion that names a batch copy, or text the judge's scan forbids, is not banked.
- Where it runs. In `prove_target` before every obligation dialog (all loops), and in one batch for several goals: the pending required theorems at the start of phase 1, the lemmas of a planner decomposition, the open helpers of each fill round, the goals of a resumed attempt, and the required theorems before the free loop's dialog. A goal is retried only when its statement or the set of complete declarations of the candidate changed.
- Budget. No model is called and no dollars are spent; every run goes through `judge.in_container`, so it stops at the run's deadline and counts against the wall cap like any other Lean run. A0 (`agents/baseline.py`) has no portfolio.
- Events: `portfolio` (label, goals, the goals closed and by which entry, batch milliseconds, attempts, whether the batch was stopped, the heartbeat limit, and per goal and entry `[closed, ms, hit heartbeat limit]`), `portfolio_bank` (goal, entry, banked text, whether it was kept), and `obligation` with `by: "portfolio"` when a dialog was not needed. `summary.json` records `portfolio` (enabled, heartbeats, seconds).
- Measurement without model calls: `agents/portfolio_replay.py` replays the goals recorded runs spent turns on, each on the candidate version on disk when its first dialog started; results in `results/feedback-1/`.

### Attempt ledger and `--resume-from`

`agents/ledger.py`. Every run of `agents/repair.py` (all loops) and `agents/baseline.py` writes `ledger.json` into its run directory (`repair.finish`):

- `proved`: every declaration that some compiling version of the candidate held with no `sorry` in its text or in any candidate declaration it mentions (transitively): name, kind, full text, the candidate declarations it depends on, the task id and the locked spec's manifest SHA-256 it was proved against. The versions are the sources `Session.compile` saw compile, so work a later rewrite lost (phase 3 replaces whole files) is kept.
- `skeletons`: the accepted top-down skeletons (round, code, open helpers, derived required theorems, plan prose).
- `open_goals`: per goal still open in the final candidate (a required theorem not proved, a helper theorem proved by `sorry`): its statement, the dialogs, turns and list-price dollars spent on it (planner calls included from their `plan` events), the last snippets tried with the first line Lean answered, the last unsolved goals Lean reported, the model's last words, planner decompositions, portfolio entries that did not close it, and whether it was refuted. For A0, which works on whole files, the turns and dollars are the run's (`scope: "run"`) and the last Lean feedback is that of the last audit.
- `best_candidate` (the version with the most required theorems proved among the `check` and A0 `audit` events, or the final one on a tie) and `final`.

`agents/repair.py --resume-from DIR[,DIR...]` (a run directory or a `ledger.json`; a run directory written before ledgers existed is reconstructed from its events and candidate versions, `agents/ledger.py RUN_DIR` prints that reconstruction):

1. A ledger is used only when its task id and spec hash are the current task's; others are refused and recorded. A reconstructed ledger gets the current spec hash only when git shows the task's lock unchanged since the run started. When none is usable the run stops before any Lean or model work.
2. Base: unless `--start` is given, each prior attempt's best and final candidate is compiled and audited (`#print axioms`) in the new session, and the compiling one with the most required theorems proved becomes the candidate.
3. Carry: the prior attempts' proved declarations are selected (required definitions stay the base's; what the base already has complete is skipped; de-duplicated by statement, keeping a duplicate only when another carried declaration names it; a declaration whose dependencies are neither in the base nor carried is dropped), installed in dependency order (a base declaration proved by `sorry` with the same statement is replaced in place, new ones go before the first base declaration that needs them) and compiled with `lake env lean --json`. Every carried declaration with an error, every carried declaration a newly broken base declaration names, and every carried declaration depending on a dropped one is dropped, and the set is compiled again until the file compiles: the largest set found this way is kept. Nothing is trusted: every carried declaration is checked by Lean in the new run.
4. The goals the prior attempts left open that are still open are worked first (`resume` phase: the portfolio in one batch, then one dialog each; in the top-down loop the helpers only, and when Lean's dependency graph shows every unproved required theorem derived from open helpers the fill phase starts on them without a new structure phase). The prior failure notes for a goal go into every prompt for that goal, and new skeleton rounds and planner prefixes start after the prior attempts' highest, so new helper names never collide with carried ones. The free loop gets the whole failure summary. Because the carried declarations can double the file (295 carried into a 107 KB candidate of rw-compound-comp gave 234 KB), a resumed run shows the obligation dialogs and the planner the candidate with long proofs of proved theorems elided (`compact_view`, as in the top-down loop; 117 KB for that file).

`agents/baseline.py --resume-from` starts A0 from the prior attempts' best compiling candidate (step 2) and appends their failure summary to the first message. Budgets are per attempt and unchanged: the Lean work of resuming counts against the new attempt's wall cap; no dollars are spent on it.

Provenance: a resumed run's `summary.json` has `resumed_from` (the prior run directories used) and `resume` (every path given with its ledger hash and why it was refused, the base, the carried and dropped declarations, the goals worked first); its own ledger repeats `resumed_from`. A Passport issued with that summary as provenance carries the optional top-level `resumed_from`; Passports without it are unchanged. Events: `resume`, `resume_base`, `resume_select`, `resume_carry`, `phase` with `resume`, `skeleton` with source `resumed`, and `audit` (A0 and phase 3: per version, compile errors or the per-theorem status).

### Goal tool and persistent Lean session (`--goal-tool on|off`, default on)

`agents/leanserver.py`. Each A1 or A2 session can hold one Lean language server (`lake env lean --server`, the toolchain's own server; nothing vendored), started on first use in the pinned image with the container command of every other Lean run (`judge.container_argv`: no network, 4 GB, 512 processes; directly inside the image with `PF_IN_IMAGE=1`). It keeps one document, `PFSession.lean`, in memory: the current candidate, or the scratch text of a snippet (the candidate followed by the snippet, built exactly as `Session._scratch` builds it). A new text is sent as one incremental edit from the first character that differs (`textDocument/didChange`, positions in UTF-16), and `textDocument/waitForDiagnostics` returns when Lean has elaborated it; Lean reuses the elaboration of every command before the edit, so a snippet after an unchanged candidate costs the snippet alone.

- `goal_at(name, line?)`, a tool of the obligation, structure and free dialogs: the proof state (`$/lean/plainGoal`: hypotheses and goals) at every `sorry` of a declaration, or at every error when it has none, or before and after one of its lines; Lean's messages in the declaration follow.
- Fast single-step check: `try_snippet` sends the scratch text to the session first. A snippet with an error or a non-linter warning (`sorry`) is answered from it, with the proof state at each `sorry` of the snippet appended, and nothing is compiled. A snippet the session finds clean is compiled as before (`lake env lean Scratch.lean`) and only that compile banks it, so the session never decides what enters the candidate.
- Limits: one of the host's container slots is held while the server elaborates; every wait stops at the run's deadline (`judge.deadline()`), so its time counts against the wall cap; a server that stops answering is killed and restarted on next use, and one that cannot start leaves the session on the compile path. A0 has no session.
- Events: `fast_check` (a snippet answered by the session, milliseconds), `goal_at` (name, line, milliseconds, errors, characters), `lean_server` (unavailable). `summary.json`: `goal_tool` (enabled, starts, start and elaboration milliseconds, elaborations, full elaborations, goal requests, timeouts, snippets rejected and found clean by the session, goal_at calls and milliseconds).

### Refutation of new helpers on concrete values (`--refute on|off`, default on)

`agents/refute.py`. A Lean probe (run like the dependency probe after `lake build Solution`, never part of a candidate) evaluates a statement on `--refute-samples` instances (default 64). The statement's binders are opened as far as `whnf` exposes them; hypotheses stay hypotheses; every other binder gets values: fixed pools for `Nat` (0 to 10^18), `Int`, `Bool`, `String`, `Option`, `List`, `Array` and pairs, structures and inductive types without indices built from their constructors with field values drawn recursively, constant functions, `Nat` for type parameters and instance resolution for instance arguments. Values from the task's own generator come first: the JSON objects and arrays inside `FLAGSHIP` and 40 `gen_case` cases of the task's `oracle.py` are converted to the binder's type by field and constructor names (a structure from an object whose keys are its field names, an inductive constructor from a string or from an object with a string naming it). Nothing is chosen per task. Fuel bounds the nesting of constructors (five levels); base types and function codomains use none. A binder that a hypothesis `a = b` fixes (it occurs on one side, alone or under constructors, as `s'` in `step s r = (.ok, s')`) is not sampled: after the free binders, its value comes from unifying its side with the other side evaluated under the heartbeat limit, so a lemma about a step is tested on the state the step produces rather than made vacuous by a random one. For each instance, the instantiated statement (hypotheses as implications) must have a `Decidable` instance, after applications of Prop-valued definitions that have none are unfolded (those that have one, such as `≤`, are kept); `decide` of it is reduced with `whnf` at full transparency under a heartbeat limit (20,000 per instance), so a recursive definition at 10^18 is undecided rather than a hang. A probe is stopped after 60 s plus 20 s per statement. An instance whose `decide` reduces to `false` refutes the statement only when Lean's kernel accepts the theorem `¬ (statement)` built from it (the statement applied to the instance, closed by `of_decide_eq_false rfl`) through the kernel's own `addDecl`.

- Where it runs, before any model turn on the statement: a planner decomposition with a false lemma is reverted and the planner is asked again with the counterexamples (within its three tries; event `plan_refuted`); a skeleton with a false open helper is rejected with the counterexample, like any other skeleton problem; `prove_target` gives a false helper no dialog and marks it refuted, so the top-down loop restructures around it and the orchestrated loop does not decompose it (`obligation` with `by: "refuted"`); `replace_declaration` with a helper stated with `sorry` is reverted when the helper is false. A statement is sampled once per context (its text and the candidate's definitions). Required theorems are never sampled.
- Statements over undecidable propositions (an `∀` left inside, a predicate without a `Decidable` instance) or over types with no values are reported as unsupported and left to the model. No dollars; the Lean time counts against the wall cap.
- Events: `refute_sample` (where, milliseconds, per statement the status `false` with instance and counterexample, `survived` with instances tried and undecided, `unsupported` with the reason, or `unconfirmed`). `summary.json`: `refute` (enabled, samples, probes, statements, false, survived, unsupported, unconfirmed, milliseconds).

### Parallel short variants (`--variants K`, default 2; `--variant-turns T`, default 2)

`agents/variants.py`. When the first obligation dialog on a goal ends without proving it, K dialogs of at most T turns start at once, each in its own copy of the session workspace (copy-on-write clone where the file system has one) and with its own output directory under `variants/`, each with a different framing of the same goal: a different route with the first attempt's failure notes, a decomposition into small helper lemmas, the library declarations ranked below the ones the first dialog was shown (without the library: case splitting on the definitions), unfolding and case splitting. Their tools are `try_snippet`, `replace_declaration`, `read_file` and the library tools. The first variant whose goal is proved (its own proof free of `sorry` and compiling, the criterion of `prove_target`) wins: the others stop before their next turn or tool call, and the winner's candidate is installed in the session only if it still compiles there. A request already sent by a stopped variant is not abandoned: its reply is discarded and its tokens charged. Every variant calls the model through `Session.call` on the run's one `Budget`, whose lock covers the dollar check and the worst-case reservation of each attempt, so requests in flight at the same time are each pre-charged at their worst case and together stay within the cap; all are settled at list price like sequential turns. Variants run once per goal, never for A0, and `--variants 0` turns them off. Events: `variants` (goal, K, T, framings), `variant_end` (per variant: turns, list dollars, ok, won, error), `variants_result` (winner, milliseconds, per variant record), `obligation` with `by: "variant"`; every event of a variant dialog carries `variant`. `summary.json`: `variants` (K, T, goals, goals won, variants, turns and list dollars in total, of won and of lost goals). Whether this pays at list price is measured in `results/feedback-2/README.md`.

### Run summary

`summary.json` of A1 and A2 records `portfolio` (enabled, heartbeats, seconds, and the run's batches, goals tried, goals closed and by which entry, Lean milliseconds, stopped batches), `goal_tool`, `refute` and `variants` as above. A0 summaries and Passports are unchanged; a Passport carries only the optional `resumed_from` from a resumed run's provenance.

## Evaluation

E1 (`eval/e1.py`) runs every arm once per task under identical caps and scores each final candidate with the judge and the binary check, outside the budget. A test run requires the approved freeze (`results/test-freeze.json`, `eval/freeze.py`), which binds the selected tasks, their validation receipts and the experiment configuration by hash; resume rejects any change. E2 (`eval/e2.py`) checks the same artifacts three ways: ordinary checking (`harness/ordinary.py`: the candidate's own project, including any spec files it ships, builds; required theorem names exist; the axiom audit is clean), the rebuild and tests alone, and ProofForge.

## PR gate

`.github/workflows/proofforge.yml` runs for pull requests from the owner, members and collaborators, and for any other pull request once a maintainer adds the `proofforge-check` label. It checks out the base branch as the trusted checker and the pull request head as data, builds the pinned image, runs `bin/proofforge check` on the PR's candidate from the trusted checkout, reproduces an accepted Passport with `bin/proofforge verify`, comments the result on the PR, uploads the Passport with the trusted checker revision, and fails unless the result is VERIFIED.

## API and deployment

`server/app.py` (FastAPI) serves:

- Jobs (`POST /api/jobs`): a replay re-emits a recorded session's events with compressed timing, labeled "Recorded run", then checks the recorded final candidate fresh; a live job runs `agents/repair.py` as a separate process (Muse Spark 1.3 on the Contributor tier with the Wonder planner by default), then checks its final candidate fresh. Events stream over server-sent events. Only public tasks are reachable; hidden variants and paths are refused.
- Tasks (`GET /api/tasks`, `GET /api/tasks/{id}`): the benchmark tasks and the real-world tasks under `realworld/tasks` (split `realworld`), each with its locked requirements; `?split=` filters by split. Hidden variants are never listed.
- Checks (`POST /api/verify`): the full Passport pipeline on a submitted candidate, under a request-wide deadline. With `"counterexample": true`, each requirement the property tests refute also gets the counterexample stage (a Lean refutation checked by the six kernels, `leanchecker` and the axiom audit), within the same deadline; the site's "Check a fix" panel sends it for the real-world tasks.
- The payout sidecar (`POST /api/payout`): the buggy and repaired executables, built once and run on a single request.
- The swap sidecar (`POST /api/swap`): one batch of at most 100 swaps on a two-token pool, run through the `swap-sidecar` of `rw-balancer-upscale` built from three fixed files (the deployed port, the plus-one hotfix and the verified Muse repair), each built once at startup. The input is rebuilt from checked whole numbers, every run shares a 20 s limit, whole numbers come back as decimal strings, and each version's committed Passport is returned only when it records that exact source file.
- The hidden challenge (`POST /api/challenge`): 300 property cases against the start candidate of a hidden flagship variant, returning a witness or UNRESOLVED.
- Operator controls (`/api/admin/*`): replay-only mode and stopping live jobs.

`server/controls.py` keeps per-client daily quotas, the live spending ledger (reserved at the per-job cap, settled at the amount charged) and the operating mode in SQLite on the data volume, and bounds concurrent jobs, live jobs, checks and challenges, answering 503 with Retry-After when full. Job records and Passports are replaced atomically; a restart marks unfinished jobs FAILED with the reason.

The API and judge run as one Fly.io Machine (performance-4x, 8 GB, a 10 GB volume) built from the committed tree by `infra/fly/deploy.sh`; the API image builds the ProofForgeFin cache of the library sources it contains (`PF_FIN_CACHE=/opt/proofforge-fin`) at image build time; the Machine is a microVM with its own kernel, so bubblewrap runs as an unprivileged user. Passports record the image by registry digest. The web front end (Next.js) is deployed to Vercel by `infra/vercel/deploy.sh`.

## Not covered

A VERIFIED requirement covers exactly its Lean statement. The JSON wrapper is tested, not proved. The judge trusts the Lean toolchain, Comparator and its sandbox, the judge image, and the owner's review of the protected spec. The pipeline does not check that the requirements describe what the owner intends; that review is the owner's.
