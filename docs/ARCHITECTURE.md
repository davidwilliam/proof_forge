# Architecture

This describes the system as built. Each section names the code that implements it.

## Components

| Component | Code | Role |
|---|---|---|
| Task | `formal/`, `tasks/<id>/`, `harness/task.py`, `harness/lock.py` | one locked Lean project: protected spec, challenge, executable wrapper, oracle |
| Judge | `harness/judge.py` | decides proof acceptance from exit codes only |
| Library | `lib/`, `harness/fin_lib.py`, `harness/FinIndex.lean` | ProofForgeFin: vendored into judged projects, bound into Passports, indexed for the repair agent |
| Binary check | `harness/binary_check.py` | rebuilds the executable and runs requirement-derived property tests |
| Counterexample stage | `harness/counterexample.py`, `counterexamples/` | turns a refuted requirement's witness into a refutation checked by the kernel |
| Passport | `harness/passport.py`, `bin/proofforge` | assembles statuses, hashes and provenance; reproduces a Passport |
| Repair agents | `agents/repair.py`, `agents/baseline.py`, `agents/meta_client.py`, `agents/budget.py` | Meta models fix the code and write the proofs |
| Evaluation | `eval/e1.py`, `eval/e2.py`, `eval/freeze.py`, `harness/ordinary.py` | completion under equal budgets (E1); integrity of checking (E2) |
| PR gate | `.github/workflows/proofforge.yml` | judges a pull request's candidate from a trusted checkout |
| API and web | `server/app.py`, `server/controls.py`, `web/` | jobs, replays, checks, Passports, the payout sidecar, the hidden challenge |
| Images and hosting | `infra/docker/`, `infra/fly/`, `infra/vercel/` | pinned Lean image; Fly.io Machine for the API and judge; Vercel for the web |

## Task

A task is a self-contained Lake project (format in `docs/TASKS.md`). `spec/<Lib>/Spec.lean` defines the requirement predicates over the implementation; `spec/<Lib>/Challenge.lean` states the definition holes and the required theorems with `sorry`; `spec/comparator.json` names the challenge and solution modules, the theorems, the definitions under repair and the permitted axioms (`propext`, `Quot.sound`, `Classical.choice`). `harness/lock.py` writes `spec/locked.json`: the SHA-256 of every protected file and a manifest hash over them. `oracle.py` is an independent Python model of the component used only by the binary check. The candidate is `candidate/Solution.lean` (and optionally `candidate/Lib/**`); it is the only input taken from an agent or a pull request.

## Judge

`judge.judge(candidate, task)` runs, in order:

1. Tree check. Every protected file present in the submitted workspace must be byte-identical to `spec/locked.json`; the lock must be internally consistent, cover exactly the protected files, and match the repository's copies.
2. Implementation scan. After stripping comments, the candidate must not contain `implemented_by`, `extern`, `unsafe`, `@[export]`, `macro`, `elab`, `syntax`, `initialize`, `#eval`, `run_cmd`, `run_elab`, `run_meta`, `native_decide`, `set_option`, `opaque`, `axiom` or `@[csimp]`, nor any other way to define or run elaboration-time code: `elab_rules`, `macro_rules`, `run_tac`, `by_elab`, simprocs, `register_*`, `declare_*` and `builtin_*` commands, module-system `meta` declarations, and attributes that register code (`@[tactic]`, `@[term_elab]`, `@[command_elab]`, `@[macro]`, `@[delab]`, `@[init]` and the like). It may import only the task's `Spec` and `Lemmas`, `Init.*`, `Std.*` and `ProofForgeFin.*` (the library below; `ProofForgeFinDemo` and `Lean` are refused). Importing `ProofForgeFin` brings `Lean` into scope, because the library's tactics are metaprograms; the metaprogram rules above are what keep candidate code from defining its own. This is defense in depth against code overrides and elaboration-time code; Comparator is the authority on statements.
3. Fresh project. A new temporary directory receives the locked project files from the repository (`lean-toolchain`, `lakefile.toml`, `lake-manifest.json`, `spec/`, `app/`) and the candidate files, nothing else. It has never been built. When a candidate file imports a `ProofForgeFin` module, the library is vendored into it (next section); otherwise the directory is exactly the locked files and the candidate.
4. Comparator: `lake comparator --paranoid --config spec/comparator.json`. Comparator builds the solution in its bubblewrap sandbox, checks that every required theorem has exactly the challenge's statement, with the definitions under repair supplied by the solution, checks that only the permitted axioms are used, and checks the declarations with six kernels: Lean's default and paranoid modes, lean4lean, nanoda, con-leche and con-ron. Any failure rejects the candidate.
5. leanchecker: `lake build Solution && lake env leanchecker Solution`, a kernel replay of the solution module's declarations. It runs without `--fresh`, so imported modules (the locked spec and Lean's core library) are loaded from their build outputs rather than replayed; Comparator's kernels above check the solution's declarations independently.
6. Axiom audit: `#print axioms` for every required theorem. The result is recorded per theorem in the Passport; enforcement of permitted axioms is Comparator's.

The candidate is accepted only if steps 1, 2 (including the library scan below), 4 and 5 succeed. Lean runs in the pinned image `proofforge-lean:4.35.0` (`infra/docker/Dockerfile.lean`: the Ubuntu 24.04 base pinned by digest, elan 4.2.4 and Lean v4.35.0 from their GitHub releases, each checked against its published SHA-256; the apt packages, among them bubblewrap, come from the Ubuntu archive at build time, so a rebuild can produce a different image digest, and every Passport records the digest it ran under). Locally each run is a `docker run --network none --memory 4g --pids-limit 512` container with the namespaces bubblewrap needs; inside the image (the Fly host, `PF_IN_IMAGE=1`) commands run directly and Comparator's sandbox applies the same way. Concurrent Lean runs per host are bounded by file locks (`PF_CONTAINER_SLOTS`, default 2). Every run has a timeout; callers can impose a request-wide deadline (`judge.time_limit`), and a run stopped by it is marked as a timeout, never as a failure of the candidate.

## ProofForgeFin in judged projects

`harness/fin_lib.py` makes the library in `lib/` (Lake package `proofforge-fin`, library `ProofForgeFin`; contents in `lib/README.md`) available to candidates.

- Version. `source_tree_sha256` is a SHA-256 over the relative path and SHA-256 of every file the package is built from: `lakefile.toml`, `lake-manifest.json`, `lean-toolchain`, `ProofForgeFin.lean` and `ProofForgeFin/**/*.lean`. `ProofForgeFinDemo`, `Audit.lean` and the docs are not part of the package, so no candidate can import the demonstrations.
- Build. Each version is built once per host, in the pinned image with no network, from those sources: `lake build ProofForgeFin ProofForgeFin:static` (the `.olean` files and the native objects an executable that imports the library links), in a cache directory keyed by the version (`PF_FIN_CACHE`, default `<tmp>/proofforge-fin`; the API image builds it at image build time). The same run writes the declaration index (`harness/FinIndex.lean`). Lake's build traces are content hashes, so a copy of the built package is up to date in any directory; a cached package whose sources do not hash to the expected version is refused.
- Vendoring. When a candidate file imports a `ProofForgeFin` module, the fresh project of the judge, of the binary check and of the counterexample stage gets the built package at `.lake/packages/proofforge-fin` (inside `.lake`, the only directory Comparator's sandbox lets a build write), a `[[require]]` with that path appended to its `lakefile.toml` and the matching path entry in `lake-manifest.json`. Comparator resolves the dependency inside its sandbox from the manifest; nothing is fetched. A candidate that imports no library module gets the same fresh project as before the integration.
- Library scan. The library modules the candidate imports, transitively, are scanned with a library policy: no `implemented_by`, `extern`, `unsafe`, `@[export]`, `@[csimp]`, `initialize`, `#eval`, `run_cmd`, `run_elab`, `run_meta`, `native_decide`, `bv_decide`, `set_option`, `opaque`, `axiom`, `sorry` or `partial`, and imports only from `ProofForgeFin`, `Init`, `Std` and `Lean`. Tactic and syntax definitions (`syntax`, `macro`, `elab_rules`, simprocs, `register_simp_attr`) are allowed in library code, not in candidate code: they change how a proof is found, not what the kernels check. The library sources are part of the trusted checkout and bound by hash in the Passport.
- Checking. The export Comparator checks contains every constant the required theorems depend on, library declarations included (1,872 declarations for `req_no_backdated` of `rw-compound-comp` with the library), so all six kernels check the library declarations a solution uses; the axiom audit covers them through `#print axioms`. `leanchecker` replays the solution module and loads the library from its build outputs, as it does for the locked spec.
- Kernel check of the library. `harness/fin_kernels.py` (test `tests/test_fin_kernels.py`) holds every library and demonstration declaration to the same kernels, so no candidate is rejected for a library declaration a kernel does not accept. It builds `lib/` in the pinned image, lists every constant its modules declare (`harness/FinDecls.lean`), exports them with the toolchain's `leanexport` plus Comparator's own export targets, and runs `lake comparator --paranoid --challenge-from-export E --solution-from-export E` with every theorem named and the judge's permitted axioms: Comparator's statement comparison, axiom check and six kernels, with its command lines and sandbox, on that export. A kernel stops at its first rejection; the checker names the declaration (con-leche and con-ron are re-run with one worker to print it), removes it and its dependents, and runs Comparator again until every kernel accepts, then checks each rejected declaration alone. The `_unsafe_rec` constants Lean compiles recursive definitions to are checked separately with `lake check --paranoid --from-export`: nanoda, con-leche and con-ron decline `unsafe` definitions by design and no proof term mentions one. `leanchecker` replays every module. A candidate's export holds the same library constants from the same build, and each kernel checks a declaration against the declarations it depends on, so the verdict per declaration carries over.

Choice. The library is vendored from the committed sources rather than baked into a new judge image. The judge image stays `proofforge-lean:4.35.0` at the digest every committed Passport records, so those Passports reproduce unchanged; a library change needs no image rebuild, only a new build of the library, keyed by the new source tree hash; the library version is visible in the repository and in the Passport rather than inside an image layer; and the build uses the same pinned toolchain and the same offline container as the judge. The cost is one library build per version per host (about 35 s for 56 modules on the development machine), and a candidate that imports the library adds the time to copy the built package (56 MB) to each fresh project.

Experiment: `tests/fixtures/library/compound_lib.lean` is a candidate for `rw-compound-comp` that imports `ProofForgeFin.DeFi`; its implementation and per-call proofs are the reference solution's, and its three sequence bounds are the library argument of `lib/ProofForgeFinDemo/DeFi/Compound.lean`. It is VERIFIED with all eight requirements, six kernels, `leanchecker` and the axioms `propext`, `Classical.choice` and `Quot.sound`, on the host and inside the image (`PF_IN_IMAGE=1`). As first written in the demonstration, four steps were accepted by Lean's kernels, lean4lean and nanoda but not by con-leche and con-ron ("fuel exhausted: whnfCore"): those two kernels unfold `doubleScale = 10 ^ 36` in equations such as `A * doubleScale + 0 = A * doubleScale`. The fixture and now the demonstration prove that arithmetic over an abstract scale and instantiate it, the agent prompt with the library says so, and `harness/fin_kernels.py` checks every library declaration against all six kernels.

## Binary check

`binary_check.check_binary` builds the task's executable (`lake build <exe>`) in another fresh project from the same locked files and candidate, records its SHA-256, and runs JSON-lines cases through it. Round 1 is the oracle's flagship case plus N generated cases (2,000 for Passports, seed 0; the E1 evaluator uses seed 1). Round 2 runs follow-up cases the oracle derives from round-1 outputs, such as resubmitting an applied transaction. `oracle.check` maps each output to requirement IDs it violates; the first six witnesses (input, output, message) are kept, plus the first witness of every further requirement, so each refuted requirement has one. A witness found on a follow-up case also records the round-1 case and output it came from (`origin`). Status is `PASS`, `REFUTED`, `BUILD_FAILED` or `TIMEOUT`.

The executable wrapper `app/Main.lean` (JSON parsing and printing) is locked but not proved; the Passport labels it tested only.

## Counterexample stage

`counterexample.run` (called by `passport.run(..., counterexample=True)` and by `bin/proofforge check` for a REFUTED candidate) takes the witness of each refuted requirement and writes a Lean theorem `<ns>.cex_<req_theorem> : ¬ (<locked statement>)`. The statement is the locked challenge's, negated; an optional per-task adapter (`counterexamples/<task or base id>.py`, or `<task>/counterexample.py`) supplies the Lean terms of the instance, and the default proof instantiates the requirement and decides the rest by kernel evaluation. In a fresh project with the locked files and the candidate, the refutation is built, then checked with `lake comparator --paranoid` against a challenge that is the locked `Challenge.lean` with the negated theorem appended, then with `leanchecker` and `#print axioms`. Details and the trust argument are in `docs/COUNTEREXAMPLES.md`.

## Passport

`passport.build` combines one judge record and one binary record:

| Requirement status | Condition |
|---|---|
| VERIFIED | the judge accepted and the binary passed every case |
| REFUTED | the binary violated this requirement on a concrete input (witness recorded) |
| UNRESOLVED | anything else, including a rejected proof without a witness and a check stopped by a time limit |

The component is VERIFIED only if every requirement is, REFUTED if any requirement is, and UNRESOLVED otherwise. The Passport records the task and manifest hashes, the statement of each requirement, the candidate and solution-tree hashes, the executable hash and the platform it was built for (for example `linux/amd64`), the Lean toolchain and judge image digest, the library record (`library`: the ProofForgeFin source tree hash available to the judge, whether it was vendored, and for a candidate that imports it the modules imported, the number of modules in their closure, the library scan, the commit whose library sources are the vendored ones, and the image and toolchain the vendored build was made with), per-check exit codes and timings, the six kernel names, the axioms per theorem, the trust assumptions, model and budget provenance when an agent produced the candidate, and a reproduce command. A REFUTED Passport issued with the counterexample stage also carries `counterexamples`: per refuted requirement, the negated statement, the witness, the Lean source of the refutation and its hash, the kernels that accepted it and its axioms, or the reason it was not checked; the requirement statuses are unchanged. `passport_sha256` is a hash of the canonical JSON without that field. `bin/proofforge verify passport.json --candidate PATH` re-runs the pipeline and compares every recorded hash and status; for a Passport with `counterexamples` it also re-checks each recorded refutation in a fresh container against a challenge regenerated from the locked files. An executable built for another CPU architecture has a different hash, so the executable hash is compared only when the machine builds for the Passport's platform; the rebuilt executable's test result is compared in every case, and the output says when the hash was not compared. Verify also compares the Lean toolchain and the library record: whether the library was vendored and, if so, its source tree hash, the modules imported and the library scan. A Passport issued before the integration has no library record, and its candidate must not import the library. A Passport whose library version is not the checkout's is reproduced with the library sources of the commit it records, extracted from git into the cache; without that commit the source tree hash is reported as different. The judge image digest is reported and counted as a difference only with `--strict-image`, because a rebuilt image can have another digest.

## Repair agents

All agents call the Meta Model API through `agents/meta_client.py` (chat completions with tool calls; transient network errors are retried within the run's deadline).

- A0, compile-and-retry (`agents/baseline.py`): Muse Spark 1.3 receives the brief, the spec and the buggy file and returns a complete `Solution.lean`; the harness replies with Lean errors, or with the axiom audit and scan violations once it compiles. No tests, snippets or planner.
- A1, harness (`agents/repair.py --planner none`): Muse Spark 1.3 works through tools in a private copy of the task without reference solutions: `read_file`, `write_solution`, `replace_declaration`, `try_snippet` (compiles a snippet after the current file and banks its proved declarations), `check` (per-theorem PROVED, SORRY or ERROR with goal states) and `run_tests` (the binary check). Phase 0 fixes behavior until the tests pass; phase 1 runs one dialog per obligation; phase 2 retries what is left; phase 3 spends any remaining budget on whole-file repair. Banking a proved snippet is transactional, and the run's result is its last compiling version.
- A2, harness with planner (`--planner muse-wonder-1.0`): in phase 2 Muse Wonder proposes helper lemma statements for an obligation that resisted direct proof; they are installed as `sorry` targets and proved by Spark, recursively to depth 2. Helpers left unproved and unused are pruned.
- Library (`agents/repair.py --library on|off`, default on; A1 and A2 only): with the library on, the session workspace has ProofForgeFin vendored, the system prompt gains a section generated from the library's declaration index (the rule that the candidate may import ProofForgeFin modules, every module with the opening of its doc, every tactic with one line on when to use it, the simp sets), the tools gain `search_library` (BM25 over each declaration's name, signature, doc string and module in the index `harness/FinIndex.lean` generates from the built library) and `add_import` (transactional), and each obligation's prompt lists the eight declarations the index ranks highest for the obligation's statement and the doc strings of the specification definitions it names. Phase 3 gets the library section without the tools. `summary.json` records `library` (enabled, source tree hash, index hash, number of entries), and `eval/e1.py --library on|off` passes the flag to A1 and A2 and records it in `config.json`. A0 is unchanged: its prompt, tools and workspace have no library. The E1 results in `results/e1-dev-2` and `results/e1-test-1` were produced before the library existed.

`agents/budget.py` enforces a dollar cap and a wall-clock cap per run. Dollars are counted at standard-tier list prices for every model, including calls served by the Contributor tier, so arms compare on one scale; the amount actually charged is tracked separately. Each call is charged its worst case before it is sent and settled from reported usage. The agent never decides acceptance; its last compiling version is judged by the shared evaluator.

## Evaluation

E1 (`eval/e1.py`) runs every arm once per task under identical caps and scores each final candidate with the judge and the binary check, outside the budget. A test run requires the approved freeze (`results/test-freeze.json`, `eval/freeze.py`), which binds the selected tasks, their validation receipts and the experiment configuration by hash; resume rejects any change. E2 (`eval/e2.py`) checks the same artifacts three ways: ordinary checking (`harness/ordinary.py`: the candidate's own project, including any spec files it ships, builds; required theorem names exist; the axiom audit is clean), the rebuild and tests alone, and ProofForge.

## PR gate

`.github/workflows/proofforge.yml` runs for pull requests from the owner, members and collaborators, and for any other pull request once a maintainer adds the `proofforge-check` label. It checks out the base branch as the trusted checker and the pull request head as data, builds the pinned image, runs `bin/proofforge check` on the PR's candidate from the trusted checkout, reproduces an accepted Passport with `bin/proofforge verify`, comments the result on the PR, uploads the Passport with the trusted checker revision, and fails unless the result is VERIFIED.

## API and deployment

`server/app.py` (FastAPI) serves:

- Jobs (`POST /api/jobs`): a replay re-emits a recorded session's events with compressed timing, labeled "Recorded run", then checks the recorded final candidate fresh; a live job runs `agents/repair.py` as a separate process (Muse Spark 1.3 on the Contributor tier with the Wonder planner by default), then checks its final candidate fresh. Events stream over server-sent events. Only public tasks are reachable; hidden variants and paths are refused.
- Tasks (`GET /api/tasks`, `GET /api/tasks/{id}`): the benchmark tasks and the real-world tasks under `realworld/tasks` (split `realworld`), each with its locked requirements; `?split=` filters by split. Hidden variants are never listed.
- Checks (`POST /api/verify`): the full Passport pipeline on a submitted candidate, under a request-wide deadline. With `"counterexample": true`, each requirement the property tests refute also gets the counterexample stage (a Lean refutation checked by the six kernels, `leanchecker` and the axiom audit), within the same deadline; the site's "Check a fix" panel sends it for the real-world tasks.
- The payout sidecar (`POST /api/payout`): the buggy and repaired executables, built once and run on a single request.
- The hidden challenge (`POST /api/challenge`): 300 property cases against the start candidate of a hidden flagship variant, returning a witness or UNRESOLVED.
- Operator controls (`/api/admin/*`): replay-only mode and stopping live jobs.

`server/controls.py` keeps per-client daily quotas, the live spending ledger (reserved at the per-job cap, settled at the amount charged) and the operating mode in SQLite on the data volume, and bounds concurrent jobs, live jobs, checks and challenges, answering 503 with Retry-After when full. Job records and Passports are replaced atomically; a restart marks unfinished jobs FAILED with the reason.

The API and judge run as one Fly.io Machine (performance-4x, 8 GB, a 10 GB volume) built from the committed tree by `infra/fly/deploy.sh`; the API image builds the ProofForgeFin cache of the library sources it contains (`PF_FIN_CACHE=/opt/proofforge-fin`) at image build time; the Machine is a microVM with its own kernel, so bubblewrap runs as an unprivileged user. Passports record the image by registry digest. The web front end (Next.js) is deployed to Vercel by `infra/vercel/deploy.sh`.

## Not covered

A VERIFIED requirement covers exactly its Lean statement. The JSON wrapper is tested, not proved. The judge trusts the Lean toolchain, Comparator and its sandbox, the judge image, and the owner's review of the protected spec. The pipeline does not check that the requirements describe what the owner intends; that review is the owner's.
